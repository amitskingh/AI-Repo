# 3 – Chat Models

## What Is a Chat Model?

A Chat Model is a LangChain interface for interacting with models using conversational messages.

Example:

```python
from langchain_openai import ChatOpenAI

model = ChatOpenAI(model="gpt-4.1-mini")
```

Conceptually:

```text
ChatOpenAI
    ↓
Chat Model
    ↓
OpenAI Model
```

The important idea is that Chat Models work naturally with a sequence of messages.

## Chat Model vs LLM

The terms are related but should not always be treated as identical.

A traditional completion-style interaction might look conceptually like:

```text
Prompt String
    ↓
Model
    ↓
Completion
```

A Chat Model works with structured conversational messages:

```text
System Message
Human Message
AI Message
    ↓
Chat Model
    ↓
AI Message
```

Modern LLM APIs commonly expose models through chat-oriented interfaces.

## Basic Chat Model

The simplest LangChain usage is:

```python
from langchain_openai import ChatOpenAI

model = ChatOpenAI(model="gpt-4.1-mini")

response = model.invoke("Explain embeddings.")

print(response.content)
```

A simple string can be used as input.

LangChain handles the appropriate model interaction behind the scenes.

## What Are Messages?

Instead of thinking only in terms of a single prompt string, Chat Models allow us to represent a conversation as messages.

For example:

```text
System:
You are a helpful Python teacher.

Human:
Explain decorators.

AI:
A decorator is...
```

These messages represent different roles in the conversation.

## Main Message Types

The important message types for now are:

```text
SystemMessage
HumanMessage
AIMessage
```

Later we will also work with:

```text
ToolMessage
```

## SystemMessage

A `SystemMessage` provides instructions or context about how the model should behave.

Example:

```python
from langchain_core.messages import SystemMessage

message = SystemMessage(content="You are a helpful Python teacher.")
```

Conceptually:

```text
SystemMessage
    ↓
How should the model behave?
```

Examples:

```text
You are a concise teacher.
You are a helpful assistant.
Answer using simple language.
Return structured information.
```

## HumanMessage

A `HumanMessage` represents user input.

Example:

```python
from langchain_core.messages import HumanMessage

message = HumanMessage(content="Explain decorators.")
```

Conceptually:

```text
HumanMessage
    ↓
What does the user want?
```

## AIMessage

An `AIMessage` represents a response generated by the AI model.

Example:

```python
response = model.invoke("Explain decorators.")
```

The response is generally an `AIMessage`.

Conceptually:

```text
AIMessage
    ├── content
    ├── metadata
    └── additional response information
```

To access the generated text:

```python
print(response.content)
```

## Explicit Message Example

We can explicitly create messages:

```python
from langchain_core.messages import (
    SystemMessage,
    HumanMessage,
)

messages = [
    SystemMessage(content="You are a concise Python teacher."),
    HumanMessage(content="Explain decorators."),
]

response = model.invoke(messages)

print(response.content)
```

Conceptually:

```text
SystemMessage
       +
HumanMessage
       ↓
   Chat Model
       ↓
    AIMessage
```

## Conversation History

A conversation can contain multiple messages.

Example:

```text
Human:
What is Python?

AI:
Python is a programming language.

Human:
What about Django?

AI:
Django is a Python web framework.
```

This can be represented as:

```python
messages = [
    HumanMessage(content="What is Python?"),
    AIMessage(content="Python is a programming language."),
    HumanMessage(content="What about Django?"),
]
```

Then:

```python
response = model.invoke(messages)

print(response.content)
```

The model can use the previous messages as context for the current request.

## Chat models do not provide memory
This is one of the most important concepts.

A Chat Model can process a sequence of messages:

```text
Messages
   ↓
Chat Model
```

But this does not mean the model permanently remembers those messages.

For example:

```python
model.invoke("My name is Alex.")
```

Then later:

```python
model.invoke("What is my name?")
```

The second call should not be assumed to know the first call.

Why?

Because the previous message was not necessarily provided again.

## Context vs Memory

This distinction is extremely important.

### Context

Context is the information that is actually provided to the model for a particular call.

For example:

```text
System Instructions
+
Conversation History
+
Retrieved Documents
+
Current User Question
```

All of this can become context for the model.

### Memory

Memory is the application-level strategy for retaining information from previous interactions and deciding what should be retrieved or provided again.

Conceptually:

```text
Conversation
    ↓
Memory / Storage
    ↓
Select Relevant History
    ↓
Context
    ↓
Chat Model
```

Therefore:

```text
Memory
    ≠
Context
```

Memory can be used to construct context.

## Memory Is Not Automatically RAM

Memory in an AI application is not necessarily computer RAM.

It can be implemented using different storage mechanisms, such as:

```text
In-memory Python object
        OR
PostgreSQL
        OR
Redis
        OR
Vector Database
        OR
Other persistent storage
```

The important concept is:

> **Memory is an application design concept, not a specific storage technology.**

## Context Window

Remember from Module 1:

The model has a context window.

Suppose a model supports a certain number of tokens.

The input might contain:

```text
System Instructions
+
Conversation History
+
Retrieved Documents
+
Current Question
```

All of this contributes to the context sent to the model.

Conceptually:

```text
             Context Window
┌────────────────────────────────────┐
│ System Instructions                │
│ Conversation History               │
│ Retrieved Information               │
│ Current User Question              │
└────────────────────────────────────┘
```

Therefore:

```text
More unnecessary context
    ↓
More tokens
    ↓
Potentially more cost
    ↓
Potentially more latency
```

## Memory → Context Relationship

A useful mental model is:

```text
                 MEMORY
                    │
                    ▼
          Select Relevant History
                    │
                    ▼
                  CONTEXT
                    │
                    ▼
               CHAT MODEL
```

Memory determines what information is retained or retrieved.

Context is what is actually sent to the model for a particular call.

## Do We Need to Send Every Conversation?

No.

A good application does not necessarily send the entire conversation forever.

It may use strategies such as:

```text
Recent messages
+
Important previous information
+
Summary
+
Relevant retrieved information
```

For example:

```text
Conversation History
        ↓
Filter / Summarize
        ↓
Relevant Context
        ↓
LLM
```

This helps manage context size, latency, and cost.

## Message History as Application Data

If you want conversation persistence, your application needs to store the relevant messages or information.

Conceptually:

```text
User Message
      ↓
Application
      ↓
Database / Storage
```

Later:

```text
New Request
      ↓
Retrieve Relevant History
      ↓
Build Messages
      ↓
Chat Model
```

The model itself should not be assumed to be your persistent conversation database.

## `invoke()`

The basic LangChain interface is:

```python
response = model.invoke("Explain embeddings.")
```

`invoke()` means:

> Execute this component with the provided input and return the result.

You'll see this pattern throughout LangChain.

Examples:

```python
model.invoke(...)
```

Later:

```python
chain.invoke(...)
```

and:

```python
retriever.invoke(...)
```

This common interface comes from the Runnable architecture.

## `invoke()` Is Synchronous

When using:

```python
response = model.invoke(...)
```

the application waits for the result before continuing.

Conceptually:

```text
Call Model
    ↓
WAIT
    ↓
Receive Result
    ↓
Continue Program
```

## `ainvoke()`

LangChain also provides an asynchronous interface:

```python
response = await model.ainvoke(...)
```

This is used inside an asynchronous function:

```python
async def main():
    response = await model.ainvoke("Explain embeddings.")

    print(response.content)
```

Conceptually:

```text
invoke()
    ↓
Synchronous

ainvoke()
    ↓
Asynchronous
```

## Why Does Async Matter?

Suppose an application needs to make several independent LLM calls.

Synchronous:

```text
Call A
 ↓
WAIT
 ↓
Call B
 ↓
WAIT
 ↓
Call C
```

Potentially:

```text
A → B → C
```

With appropriate asynchronous design, independent calls can potentially overlap:

```text
       ┌→ Call A ─┐
Start ─┼→ Call B ─┼→ Results
       └→ Call C ─┘
```

This can improve throughput when the workload is I/O-bound.

We will study this properly in:

**Module 2.12 – Async LangChain**

## `invoke()` vs `ainvoke()`

| Method | Purpose |
|---|---|
| `invoke()` | Synchronous execution |
| `ainvoke()` | Asynchronous execution |

Example:

```python
response = model.invoke("Hello")
```

versus:

```python
response = await model.ainvoke("Hello")
```

## Common Mistakes

#### Chat Model automatically remembers previous conversations.

Incorrect.

The application must provide the relevant history.

#### `AIMessage` is memory.

Incorrect.

`AIMessage` is a message object representing an AI response.

#### Chat Model = Memory.

Incorrect.

A Chat Model processes messages.

Memory is an application-level strategy for retaining/retrieving information.

#### SystemMessage is the user's message.

Incorrect.

```text
SystemMessage → Instructions / behavior
HumanMessage  → User input
AIMessage     → Model response
```

#### Calling `invoke()` twice automatically gives the second call the first call's conversation.

Incorrect.

Each call only has access to the input/context provided to it, subject to the provider's API behavior.

#### `invoke()` is asynchronous.

Incorrect.

`invoke()` is the synchronous interface.

Use `ainvoke()` for asynchronous execution.

#### More conversation history is always better.

Incorrect.

Unnecessary history increases context usage and can increase cost and latency.

It can also introduce irrelevant information.

## Best Practices

### Use Appropriate Message Roles

```text
SystemMessage
    ↓
Instructions

HumanMessage
    ↓
User Input

AIMessage
    ↓
Model Response
```

### Don't Send Unnecessary History

Prefer:

```text
Relevant History
+
Current Request
```

over:

```text
Entire Conversation Since Day One
```

when the older information is irrelevant.

### Treat Conversation History as Application Data

If persistence is required:

```text
Messages
    ↓
Database / Storage
```

The Chat Model should not be treated as a persistent database.

### Keep Context Focused

A useful principle:

> **More context does not automatically mean better context.**

Send the information relevant to the current task.

### Understand Sync vs Async

Use:

```python
invoke()
```

for synchronous execution.

Use:

```python
await ainvoke()
```

when asynchronous execution is appropriate.
