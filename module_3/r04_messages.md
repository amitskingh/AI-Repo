# 4 – Messages: System, Human, AI & Tool Messages

## What Is a Message?

A message is a structured piece of information exchanged during an LLM interaction.

Instead of thinking only in terms of:

```text
Prompt
   ↓
LLM
   ↓
Response
```

we can think in terms of:

```text
Message
Message
Message
Message
...
```

Each message has a role and content.

Conceptually:

```text
System → Instructions
Human  → User Input
AI     → Model Response
Tool   → Tool Result
```

## Why Do Messages Have Roles?

Consider:

```text
You are a Python teacher.

Explain decorators.
```

A human can understand:

```text
"You are a Python teacher."
    ↓
Instruction

"Explain decorators."
    ↓
User Request
```

LangChain can explicitly represent these roles:

```text
System:
You are a Python teacher.

Human:
Explain decorators.
```

This makes the purpose of each message clear.

## Main Message Types

The important message types are:

```text
SystemMessage
HumanMessage
AIMessage
ToolMessage
```

| Message         | Purpose                                 |
| --------------- | --------------------------------------- |
| `SystemMessage` | Instructions/context for model behavior |
| `HumanMessage`  | User input                              |
| `AIMessage`     | AI/model response                       |
| `ToolMessage`   | Result returned from tool execution     |

## SystemMessage

`SystemMessage` provides instructions or context that influence how the model should behave.

Example:

```python
from langchain_core.messages import SystemMessage

message = SystemMessage(content="You are an expert Python teacher.")
```

Conceptually:

```text
SystemMessage
      ↓
How should the model behave?
```

Examples:

```text
You are a Python tutor.
Answer concisely.
Use simple examples.
Return structured information.
```

## HumanMessage

`HumanMessage` represents user input.

Example:

```python
from langchain_core.messages import HumanMessage

message = HumanMessage(content="Explain decorators.")
```

Conceptually:

```text
HumanMessage
      ↓
What does the user want?
```

## AIMessage

`AIMessage` represents a response generated by the AI model.

Example:

```python
response = model.invoke("Explain decorators.")
```

The response is generally an:

```text
AIMessage
```

The generated text can be accessed with:

```python
print(response.content)
```

Conceptually:

```text
HumanMessage
      ↓
Chat Model
      ↓
AIMessage
```

## ToolMessage

`ToolMessage` represents the result of executing a tool.

Example flow:

```text
Human:
What's the weather in Delhi?

AI:
Call get_weather("Delhi")

Tool:
30°C and sunny

AI:
The weather in Delhi is 30°C and sunny.
```

The tool result is represented by:

```text
ToolMessage
```

Conceptually:

```text
AIMessage
   ↓
Tool Call
   ↓
Tool Execution
   ↓
ToolMessage
   ↓
AIMessage
```

## Tool vs ToolMessage

This distinction is extremely important.

### Tool

A Tool is the actual capability/function.

Example:

```python
@tool
def get_weather(city: str):
    return "30°C and sunny"
```

Here:

```text
get_weather()
    ↓
Tool / Capability
```

### ToolMessage

The `ToolMessage` contains the result produced by the tool execution.

```text
get_weather()
    ↓
"30°C and sunny"
    ↓
ToolMessage
```

Therefore:

```text
Tool
    ≠
ToolMessage
```

#### Core idea
> **Tool = capability**

> **ToolMessage = tool execution result carried as a message**

## AIMessage Can Contain Tool Calls

An `AIMessage` does not always contain only natural-language text.

When the model decides that a tool is needed, the `AIMessage` can contain tool-call information.

Conceptually:

```text
AIMessage
├── content
└── tool_calls
```

Example:

```python
AIMessage(content="", tool_calls=[{"name": "get_weather", "args": {"city": "Delhi"}}])
```

The important idea is:

> The AIMessage contains a request to use a tool. It does not execute the tool.

## Complete Tool Calling Flow

Suppose the user asks:

```text
What's the weather in Delhi?
```

The flow becomes:

```text
HumanMessage
      ↓
LLM
      ↓
AIMessage
(tool call)
      ↓
Application
      ↓
Tool Execution
      ↓
ToolMessage
      ↓
LLM
      ↓
AIMessage
(final answer)
```

## Step-by-Step Example

### Step 1 – User Message

```text
HumanMessage

content:
"What's the weather in Delhi?"
```

### Step 2 – Model Decides to Use a Tool

The model generates an `AIMessage` containing a tool call:

```text
AIMessage

tool_calls:
    name: get_weather
    args:
        city: Delhi
```

The model is essentially saying:

> "I want the application to execute `get_weather` with `Delhi`."

### Step 3 – Application Executes the Tool

The application executes:

```python
get_weather("Delhi")
```

Important:

```text
LLM
    ≠
Tool Executor
```

The application executes the function.

### Step 4 – Tool Result

The tool returns:

```text
30°C and sunny
```

The application represents the result as:

```text
ToolMessage

content:
"30°C and sunny"
```

### Step 5 – Model Receives the Tool Result

The model now receives the relevant message sequence:

```text
Human:
What's the weather in Delhi?

AI:
[Call get_weather]

Tool:
30°C and sunny
```

### Step 6 – Final AI Response

The model generates:

```text
AIMessage

content:
"The weather in Delhi is 30°C and sunny."
```

## Complete Message Sequence

The entire interaction can be represented as:

```text
┌─────────────────────────────────────┐
│ HumanMessage                        │
│ "What's the weather in Delhi?"      │
└──────────────────┬──────────────────┘
                   ↓
┌─────────────────────────────────────┐
│ AIMessage                           │
│ tool_call: get_weather("Delhi")     │
└──────────────────┬──────────────────┘
                   ↓
              Application
                   ↓
              get_weather()
                   ↓
┌─────────────────────────────────────┐
│ ToolMessage                         │
│ "30°C and sunny"                    │
└──────────────────┬──────────────────┘
                   ↓
┌─────────────────────────────────────┐
│ AIMessage                           │
│ "The weather is 30°C and sunny."    │
└─────────────────────────────────────┘
```

## Correction

Do NOT think:

```text
AIMessage
    ├── ToolMessage
    └── Content
```

The `ToolMessage` is not simply a field inside the `AIMessage`.

Instead, they are separate messages in the conversation sequence:

```text
HumanMessage
      ↓
AIMessage
(tool call)
      ↓
ToolMessage
(tool result)
      ↓
AIMessage
(final answer)
```

This distinction is very important for understanding agents later.

## Who Combines Everything?

There isn't necessarily a magical LangChain operation that combines:

```text
AIMessage + ToolMessage
```

into one final message.

Instead, the messages form a sequence.

The application/framework sends the relevant sequence back to the model:

```text
HumanMessage
+
AIMessage
+
ToolMessage
```

The model then generates another:

```text
AIMessage
```

So think:

```text
Message 1
Message 2
Message 3
Message 4
```

rather than:

```text
AIMessage
    +
ToolMessage
    ↓
Combined AIMessage
```

## The LLM Is Always the LLM

Another important clarification:

Do not think the model chooses between:

```text
Tool
OR
LLM
```

The LLM is involved in both situations.

The actual decision is:

```text
LLM
 │
 ├── Answer directly
 │
 └── Request a tool
```

## Example Without a Tool

User asks:

```text
What is Python?
```

Flow:

```text
HumanMessage
      ↓
LLM
      ↓
AIMessage
(final answer)
```

No tool is needed.

## Example With a Tool

User asks:

```text
What's the weather in Delhi?
```

Flow:

```text
HumanMessage
      ↓
LLM
      ↓
AIMessage
(tool call)
      ↓
Application
      ↓
Tool
      ↓
ToolMessage
      ↓
LLM
      ↓
AIMessage
(final answer)
```

The LLM participates in both flows.

## Message History

A conversation can contain multiple messages.

Example:

```python
messages = [
    HumanMessage(content="What is Python?"),
    AIMessage(content="Python is a programming language."),
    HumanMessage(content="What is Django?"),
]
```

Then:

```python
response = model.invoke(messages)
```

The model can use the previous messages as context.

## Messages Are Data

Think of messages as structured application data.

Example:

```python
messages = [
    SystemMessage(...),
    HumanMessage(...),
    AIMessage(...),
    ToolMessage(...),
]
```

The list represents the conversation/message state being passed between components.

Conceptually:

```text
messages
    ↓
Chat Model
    ↓
AIMessage
```

## Message History Is Not Automatically Persistent

Suppose we store messages in a Python list:

```python
messages = [
    HumanMessage(content="My name is Alex."),
    AIMessage(content="Nice to meet you, Alex."),
]
```

While the application is running:

```text
Python List
    ↓
Messages
```

But if the application terminates:

```text
Application Stops
       ↓
Python List Disappears
```

If persistence is required:

```text
Messages
   ↓
PostgreSQL / Redis / Other Storage
```

Later:

```text
Storage
   ↓
Retrieve History
   ↓
Messages
   ↓
Chat Model
```

## Memory vs Message History

These are related but not identical.

### Message History

The actual sequence of messages:

```text
HumanMessage
AIMessage
HumanMessage
AIMessage
```

### Memory

The broader application mechanism that determines what information should be retained and retrieved.

Conceptually:

```text
Memory / Storage
       ↓
Select Relevant Information
       ↓
Message History / Context
       ↓
Chat Model
```

Therefore:

```text
Message History
    ≠
Memory
```

## Context vs Memory

Context is what is actually provided to the model for a particular call.

For example:

```text
System Instructions
+
Relevant Conversation History
+
Retrieved Documents
+
Current Question
```

This becomes the model's context.

A useful relationship is:

```text
Memory
   ↓
Retrieve Relevant Information
   ↓
Messages
   ↓
Context
   ↓
Chat Model
```

## Context Window

Every message included in a model request contributes to the input/context.

For example:

```text
SystemMessage
+
HumanMessage
+
AIMessage
+
HumanMessage
+
ToolMessage
+
Current HumanMessage
```

All of this consumes context-window capacity.

Therefore:

```text
More unnecessary messages
       ↓
More tokens
       ↓
More context usage
       ↓
Potentially more cost/latency
```

## More Context Is Not Always Better

Do not assume:

```text
More History
    =
Better Answer
```

Unnecessary history can:

* Increase token usage
* Increase cost
* Increase latency
* Distract the model
* Introduce irrelevant information

Prefer:

```text
Relevant History
+
Current Request
```

instead of blindly sending the entire conversation.

## Message Content

Message content does not always have to be a simple text string.

Depending on the model/provider, content can represent structured multimodal information such as:

```text
Text
Images
Other Content Blocks
```

Conceptually:

```text
HumanMessage
    ├── Text
    └── Image
```

The exact representation depends on the model provider and LangChain integration.

## Message Metadata

Messages can contain additional information.

Conceptually:

```text
AIMessage
├── content
├── metadata
├── response information
└── tool_calls
```

Depending on the provider and integration, this may include information related to:

* Token usage
* Model information
* Finish reason
* Tool calls
* Response metadata

Exact fields depend on the provider and LangChain version.

## SystemMessage Is Not a Security Boundary

Suppose we write:

```text
System:
Never delete a community.
```

This is an instruction to the model.

It is NOT a security mechanism.

A production application should still enforce:

```text
Authentication
Authorization
Input Validation
Business Rules
Confirmation
Risk Checks
```

Therefore:

> **Prompt instructions are behavior guidance, not authorization controls.**

## Example – HOA Assistant

Suppose we build an HOA assistant.

User:

```text
Show me the rules about parking.
```

The system may conceptually produce:

```text
SystemMessage
"You are an HOA assistant."

HumanMessage
"Show me the rules about parking."

AIMessage
"Search the HOA documents."

ToolMessage
"[Relevant parking rules]"

AIMessage
"According to the community documents..."
```

The message sequence is:

```text
SystemMessage
      ↓
HumanMessage
      ↓
AIMessage
(tool call)
      ↓
ToolMessage
      ↓
AIMessage
(final answer)
```

This is very close to the workflows we will eventually build with RAG and agents.

## Common Mistakes

#### ToolMessage is the tool.

Incorrect.

```text
Tool
    ↓
Capability / Function

ToolMessage
    ↓
Tool Execution Result
```

#### AIMessage always contains only text.

Incorrect.

It can contain additional information such as tool calls and metadata.

#### AIMessage executes the tool.

Incorrect.

The application executes the tool.

#### ToolMessage is nested inside AIMessage.

Incorrect.

They are separate messages in the sequence.

#### SystemMessage provides application security.

Incorrect.

Security must be enforced by the application/backend.

#### Messages automatically persist.

Incorrect.

Persistence requires storage.

#### Message History = Memory.

Not exactly.

Message history is the actual sequence of messages.

Memory is the broader application mechanism for retaining/retrieving information.

#### More messages always mean better context.

Incorrect.

Relevant context is generally more useful than unnecessary history.

## Best Practices

### Use the Correct Message Role

```text
SystemMessage
    ↓
Instructions

HumanMessage
    ↓
User Input

AIMessage
    ↓
Model Response

ToolMessage
    ↓
Tool Result
```

### Keep History Relevant

Don't blindly send every previous message.

### Store Persistent History Externally

Depending on requirements, use:

```text
PostgreSQL
Redis
Other Persistent Storage
```

### Don't Use Prompts as Security

System prompts can guide behavior but cannot replace:

```text
Authentication
Authorization
Validation
Business Rules
```

### Inspect Message Sequences During Debugging

For tool-calling workflows, inspect:

```text
HumanMessage
      ↓
AIMessage(tool_call)
      ↓
ToolMessage
      ↓
AIMessage(final)
```

This makes debugging much easier.
